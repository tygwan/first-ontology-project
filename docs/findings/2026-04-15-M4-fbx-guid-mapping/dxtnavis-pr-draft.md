# Improve gap_fallback.fbx downstream usability: sidecar index, locale-independent property names, individual GLB option

## Summary

While integrating DXTnavis exports into a downstream Python pipeline (`bimkg`, a BIM knowledge-graph builder for SP3D plant models), we ran into three friction points when consuming `gap_fallback.fbx` — the bundled mesh file that carries the 788 `fbx_supplemented` objects that do **not** have individual `mesh/{object_id}.glb` counterparts.

The issues below are ordered by downstream impact. All findings were reproduced against the snapshot `2026-04-07` generated by DXTnavis `v1.4.0`. A minimal, standalone audit script (`fbx_parser_demo.py`, ~150 LOC, stdlib only) is attached as reproducible evidence.

| # | Issue | Severity | Affected meshes |
|---|---|---|---|
| 1 | Property key `항목 - GUID` is Korean-localized | Major (locale-dependent parsing) | 740 / 788 |
| 2 | 48 `Geometry` meshes have no GUID at all | Major (cannot map to Gold) | 48 / 788 |
| 3 | No external `mesh_index → ObjectId` index file | Major (forces binary parsing) | 788 / 788 |
| 4 | X-axis inverted vs. `geometry.csv` coordinates | Minor (documentation) | 788 / 788 |

The single most impactful improvement would be **Alternative 1 below** (individual GLB export), which would eliminate issues 1–3 in one step.

---

## Issue 1 — Korean-localized property key `항목 - GUID`

### Observation

In `gap_fallback.fbx`, each `Model::Mesh` node stores its SP3D ObjectId inside `Properties70` under a Korean-localized key:

```
Properties70:  {
    P("항목 - GUID", "KString", "", "U", "ed66a072-0dc2-581a-aa20-a94ddab48ce3")
    P("SmartPlant 3D - SP3d Moniker", "KString", "", "U", "@a=0028!!140039...")
    P("SmartPlant 3D - SP3d Name", "KString", "", "U", "Utility_FOUR_HOLE_PLATE_4-1-C8")
    P("SmartPlant 3D - SP3d System Path", "KString", "", "U", "Assy_FR_UC_CS_1-1-2")
}
```

The string `항목 - GUID` translates roughly to "Item - GUID". The two `SmartPlant 3D - …` keys are English, which makes the Korean one stand out.

### Why it matters downstream

- Any parser written in a non-Korean locale either has to embed the literal UTF-8 byte sequence (`\xed\x95\xad\xeb\xaa\xa9 - GUID`) or be locale-aware.
- Static analysis, grep, and IDE tooling all treat the literal as an opaque blob.
- Third-party FBX viewers (e.g. Blender's property inspector, Autodesk FBX Review) display the key correctly but do not offer a stable English alias.

### Suggested fix

Emit the GUID under an English, locale-independent key — either *in addition to* or *instead of* the current one:

```
P("ObjectId", "KString", "", "U", "ed66a072-0dc2-581a-aa20-a94ddab48ce3")
# or
P("SmartPlant 3D - SP3d GUID", "KString", "", "U", "ed66a072-0dc2-581a-aa20-a94ddab48ce3")
```

Using the `SmartPlant 3D - …` namespace (already established for `SP3d Moniker`, `SP3d Name`, `SP3d System Path`) would be the most consistent choice and wouldn't break any existing Korean-aware consumer.

## Issue 2 — 48 `Geometry` meshes have no GUID at all

### Observation

Of the 788 `Model::Mesh` entries in `gap_fallback.fbx`:

- **740** (93.9%) expose `항목 - GUID` in their `Properties70` block.
- **48** (6.1%) expose **none** of: `항목 - GUID`, `SmartPlant 3D - SP3d Moniker`, `SmartPlant 3D - SP3d Name`, or `SmartPlant 3D - SP3d System Path`.

All 48 of the missing-GUID meshes share the literal node name `Model::Geometry` (empty `SP3d Name`), and all 48 are geometrically identical:

- `vertex_count` = 1728 (exact match across all 48)
- bounding box = 0.07 m × 0.19 m × 0.19 m
- Strongly suggests these are **template instances of a single Flange part**, inlined once per occurrence.

### Why it matters downstream

Because we cannot extract a GUID, we cannot deterministically link these 48 meshes to rows in our Gold layer (our canonical `object_id` keyed table). In the `bimkg` pipeline, this forces one of three bad choices:

1. Drop the 48 meshes → visual gaps in the 3D viewer.
2. Hash their geometry and hope for a unique match → brittle, position-dependent.
3. Fall back to positional nearest-neighbor against `geometry.csv` → O(n²) and ambiguous when flanges cluster.

### Supporting evidence

See `evidence/fbx_48_missing_guid.csv` in this finding folder for the full enumeration (mesh_index, vertex_count, bbox, node_name).

### Suggested fix

**Preferred**: Populate `항목 - GUID` (or its English replacement per Issue 1) for these 48 meshes. If they are true template instances that *share* an underlying SP3D object, emit the GUID of that underlying object on every instance.

**Acceptable fallback**: Emit an `InstanceOf` property pointing to a template GUID, plus a per-instance `InstanceIndex`:

```
P("SmartPlant 3D - TemplateOf", "KString", "", "U", "<template-guid>")
P("SmartPlant 3D - InstanceIndex", "Int", "", "U", 0)
```

## Issue 3 — No external `mesh_index → ObjectId` index file

### Observation

Today, extracting the 740 available GUIDs requires walking the FBX binary (node `Objects` → `Geometry`/`Model` nodes → `Properties70` → matching the Korean property key). There is no companion CSV/JSON sidecar.

### Why it matters downstream

- FBX is a proprietary binary format. Parsing it from Python requires either `fbx-sdk` (platform-limited, non-pip), a hand-rolled binary reader, or round-tripping through Blender/Assimp — each with non-trivial install friction for CI environments and Foundry transforms.
- The 93.9% success case still forces every downstream consumer to re-implement the same extraction logic, duplicating work and risk.

### Suggested fix

Emit a companion CSV alongside `gap_fallback.fbx` on every export:

```csv
# gap_fallback_index.csv
mesh_index,object_id,sp3d_name,sp3d_moniker,sp3d_display_name,sp3d_system_path
0,ed66a072-0dc2-581a-aa20-a94ddab48ce3,Utility_FOUR_HOLE_PLATE_4-1-C8,@a=0028!!140039...,Utility_FOUR_HOLE_PLATE_4-1-C8,Assy_FR_UC_CS_1-1-2
1,...
...
787,...
```

Column semantics:

| Column | Meaning |
|---|---|
| `mesh_index` | 0-based index in the FBX `Objects/Geometry` enumeration order |
| `object_id` | SP3D GUID (empty for the 48 `Geometry` instances until Issue 2 is fixed) |
| `sp3d_name` | Value of `SmartPlant 3D - SP3d Name` |
| `sp3d_moniker` | Value of `SmartPlant 3D - SP3d Moniker` |
| `sp3d_display_name` | FBX node display name (typically equals `sp3d_name`, `"Geometry"` otherwise) |
| `sp3d_system_path` | Value of `SmartPlant 3D - SP3d System Path` |

JSON (`gap_fallback_index.json`) would be equally acceptable; CSV is slightly easier to diff and stream.

## Issue 4 (optional) — Coordinate system convention

### Observation

- FBX X-axis spans `[-51.00, -1.52]`.
- Gold `geometry.csv` X-axis spans `[+1.52, +50.98]`.
- Y and Z ranges match sign-for-sign.

This looks like a left-hand ↔ right-hand coordinate flip applied only to the FBX output (Autodesk FBX is LH by default; SP3D export appears to be RH).

### Suggested fix

Either:

- Apply the coordinate flip at export time so FBX and CSV agree, **or**
- Document the convention explicitly in the DXTnavis README (e.g. "gap_fallback.fbx is left-handed; multiply X by −1 to align with geometry.csv").

The second option is cheaper and sufficient for our use case.

## Alternative 1 (strongly preferred) — Individual GLB export

Rather than patch issues 1–3 incrementally, the cleanest solution is to **remove the FBX bundle entirely** and export one GLB per `fbx_supplemented` object, matching the existing `mesh/` convention:

```
mesh/{object_id}.glb         # already exists for non-fallback objects
mesh/{object_id}.glb         # NEW — one per fbx_supplemented object
```

Downstream benefits:

- **Uniform file format.** `bimkg` can drop its FBX code path entirely.
- **1:1 Foundry Media Set upload.** Each GLB becomes a single media asset keyed by `object_id`, no bundle-unpacking transform required.
- **WebGL-friendly.** `<model-viewer>` and Three.js both load GLB natively.
- **Issues 1, 2, and 3 disappear.** The filename *is* the index; there is no locale-specific property to parse; missing GUIDs become impossible to emit (the exporter must know the GUID to name the file).

We understand this is a larger change on the DXTnavis side. If individual GLB is not feasible in the short term, the sidecar CSV (Issue 3) is the next-best step.

## Quantified impact on our pipeline

Concrete numbers from the `bimkg` adjacency analysis (snapshot `2026-04-07`, DXTnavis `v1.4.0`):

- **788** `Model::Mesh` entries in `gap_fallback.fbx` — exact match with 788 `fbx_supplemented` objects in Gold.
- **740 / 788 (93.9%)** successfully mapped via `Properties70["항목 - GUID"]`.
- **48 / 788 (6.1%)** currently unmappable (all named `Geometry`).
- The 788 objects participate in **20,746 adjacency edges** (9.4% of the total 110,173 spatial relations).
- Removing them fragments **40 / 142 pipelines (28.2%)**.
- **64** of them are **articulation points** in the construction graph — i.e. losing their identity actively breaks connectivity analysis, not just visualization.

In short: this is the single largest remaining blocker to a fully deterministic DXTnavis → Foundry pipeline on our side.

## Our downstream commitment

On the `bimkg` side we will:

- Update the FBX parser to **prefer** the new sidecar (`gap_fallback_index.csv`) when present.
- Keep the binary FBX `Properties70` walker as a fallback for older snapshots (backward compatibility).
- Switch the `object_id` lookup key from the Korean literal to the English alias as soon as it ships, without dropping the Korean path until a full deprecation cycle has passed.
- Archive the full investigation (audit script, evidence CSVs, figures) under our finding `M4-fbx-guid-mapping` so future maintainers can reproduce the analysis.
